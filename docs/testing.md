# 测试方案（Testing）

> 适用对象：bodymd 工作流仓库。**没有传统意义的单元测试**，因为核心交付物是文档与数据契约，不是二进制。
> 因此测试分四层，其中**第一层是唯一可以自动化的**。

---

## 一、测试分层

| 层级 | 测什么 | 手段 | 自动化 |
|---|---|---|---|
| **L1 契约测试** | `log/` 文件是否符合数据契约 | `scripts/validate_log.py` | ✅ 可自动 |
| **L2 工作流测试** | 四个工作流能否产出规定格式 | 人工按验收标准走一遍 | ❌ 人工 |
| **L3 合规测试** | 输出是否触碰合规红线 | 人工检查输出文本 | ❌ 人工（可用关键词脚本辅助） |
| **L4 跨模型测试** | 换模型后是否仍然可用 | 同一份输入喂 3 个模型，比对输出结构 | ❌ 人工 |
| **L5 饮食结构测试** | 非西方餐食的识别与追问是否触发 | 用 `examples/fixtures/` 跨菜系数据 | ❌ 人工 |

## 二、L1 契约测试（自动化）

### 2.1 校验项

| 编号 | 校验内容 | 失败等级 |
|---|---|---|
| V1 | 餐食行字段数 ≥ 6 | 🔴 致命 |
| V2 | 餐食行存在 `source` 字段 | 🔴 致命 |
| V3 | 餐食行的 `source` 取值属于餐食合法集合 | 🔴 致命 |
| V4 | 餐食行必须有 `edited` 字段 | 🟠 警告 |
| V5 | kcal / protein 为数字或显式 `unknown` | 🔴 致命 |
| V6 | 训练行必须有 `exercise` / `reps` | 🔴 致命 |
| V7 | 训练行的 `load_kg` 存在（可为 `bodyweight` / `unknown`） | 🟠 警告 |
| V8 | 时间格式为 `HH:MM` | 🟠 警告 |
| V9 | `## Meals` / `## Training` 段落存在 | 🟡 提示 |

⚠️ **V2 与 V3 的顺序**：代码先查字段是否存在（V2），再查取值是否合法（V3）。文档曾经写反过。

⚠️ **合法 `source` 取值是按记录类型分的**，`{photo, voice, manual, wearable, video+voice, estimated}`
只是**餐食行**的集合，校验器也只查餐食行。训练 / `## Body` / `## Sleep` 各用各的集合
（`sleep` 一栏刻意不写死，因为设备名单每年都在变）。完整表格见 `SKILL.md` §3.4 ——
这一条当年踩过坑：文档只公布了 6 个值，而仓库里实际用了 15 个。

**设计原则**：**能降级为警告的，绝不当致命错误。** 用户的记录不完整是常态，校验器的职责是提示，不是拒绝。

### 2.2 运行

```bash
python3 scripts/validate_log.py examples/fixtures/
python3 scripts/validate_log.py log/
```

退出码：`0` 全部通过｜`1` 存在致命错误｜`2` 仅警告

### 2.3 通过标准

**全部 fixture 必须通过（0 致命错误）。** 这是提交前的硬门槛。

## 二·B、自检断言清单（`scripts/selftest.py`）

`scripts/selftest.py` 的每一条断言都必须对应下表的一行承诺。改脚本时必须同步改这张表 ——
**表里没有的断言不许存在**，否则它就只是"大概对了"。

```bash
python3 scripts/selftest.py            # 21 项 → 21/21 PASS
python3 scripts/selftest.py --verbose  # 通过项也打印细节
```

| 断言 | 承诺 | 类型 |
|---|---|---|
| T1 | 43 个必需文件齐全 | 结构 |
| T2 | `SKILL.md` 有 `name` / `description` 头 | 结构 |
| T3 | `AGENTS.md` / `.cursor/rules/` / copilot 三个适配层都指向 `SKILL.md` | 结构 |
| T4 | 9 个合成档案都带 `SYNTHETIC` 标记 | 合规 |
| T5 | 9 个 fixture 契约校验 0 致命 | 契约 |
| T6 | 警告**只**出现在故意留警告的 `MX-01`（证明"降级为警告"成立） | 契约 |
| T7 | 聚合得到 75 天 / 9 个档案 | 聚合 |
| T8 | 缺 `## Totals` 的 6 天正确回退为逐餐累加 | 聚合 |
| T9 | 完全没有 `## Totals` 的那天：摄入可重算，**缺口必须是 unknown，不是 0** | 聚合 |
| T10 | 每天的 `Totals` 与逐餐累加自洽（±5%） | 聚合 |
| T11 | 关键样本值（MX-01 严重蛋白缺失日 = 48 g）不被悄悄算错 | 聚合 |
| T12 | 同一输入两次解析结果完全一致 | 确定性 |
| T13 | 9 个 fixture 的所有餐食/训练行都带 `source` | 契约 |
| T14 | **一天一文件布局下，身份标签取目录名**（1 个档案，不是 7 个） | 聚合 |
| T15 | 可选字段（`order_ok` / `## Body` / `## Supplements`）既不报错也不丢数据 | 契约 |
| T16 | **文档里的示例日志行符合契约**（用同一把尺子量文档与用户日志） | 文档 |
| T16b | **文档里出现的每个 `source` 取值都是公布过的** | 文档 |
| T17 | **单次训练消耗 ≠ 全天消耗**，两个字段不互相污染 | 聚合 |
| T18 | **两周必须分成两个 ISO 周**，且体重趋势按 7 天均值算出（首周为 `——`）；跨两周的档案集合固定为 `CN-01` / `CN-02` | 聚合 |
| T19 | **蛋白达标按 90% 阈值、且逐档案用自己的目标**（含 135 g/134.9 g 边界探针；分母是**记录天数** —— `DE-01` 的 5 天周把 `1/5` 和硬编码的 `1/7` 分开） | 聚合 |
| T20 | **一周称重不足 4 天时，体重均值与趋势都必须退化为 `——`**（含 3 天 / 4 天两侧探针；`CN-02` 的 W39 连续 5 天缺测，W38 的 4 次称重仍算得出均值） | 聚合 |

⭐ **T16 是这张表里最贵的一条。** 最贵的缺陷不是脚本算错，而是**文档给出的示例本身就违反自己
定义的契约** —— 用户会照抄它，而那是他第一天唯一的一次尝试。这类缺陷在本仓库真实发生过 5 次，
所以它被写成了一条自动断言。

⭐ **T16b 来自一次真实的量表事故**：文档只公布了 6 个合法 `source` 取值，而仓库里实际用了 15 个 ——
`wearable` 公布了却 **0 次**使用，`scale` / `tape` / `self-report` / `video` 用了却从没公布。
**一份「合法取值」清单如果和真实用法不一致，它就不是契约，是装饰。**

⭐ **T14 与 T17 也都来自真实的错误**：T14 来自"一个真人被报成 7 个档案"，T17 来自"把 260 kcal
的单次训练消耗当成了 2,650 kcal 的全天消耗"。**先犯错，再把它变成断言** —— 这张表就是本项目的
错题本。

⭐ **T18 与 T19 来自同一个发现：整条"周对周"路径零覆盖。**
全部 8 个 fixture 都只有一周（09-14 → 09-20），而 `parse_log.py` 当时按**档案**聚合、
**没有"周"这个概念** —— 于是文档承诺的体重趋势永远算不出来，`workflows/04-weekly-review.md`
里"连续两周平台期"那条规则**永远无法被触发**。文档写了、代码没有、测试看不见，三者凑齐就是
一个永远不会报错的空洞。

修法分两步，缺一不可：

1. **让 fixture 长出第二周**（`CN-01` 补 09-07 → 09-13）—— 没有两周的数据，任何断言都只是纸面声明；
2. **让聚合器按 ISO 周分组**，并把蛋白达标（90% 阈值、逐档案目标）真正算出来。

T19 里额外埋了一个**边界探针**（目标 150 g 时，135.0 必须算达标、134.9 必须不算）。
理由是：交叉验证用的是同一个阈值常量，把 90% 改成 100% 时**它会跟着一起错** ——
只有写死边界的探针能抓住这种"一致地错"。

⭐ **`DE-01` 的 5 天周（部分周）没有新增断言，它用的是既有断言。** 在它之前，集合里每一个
「档案-周」都恰好 7 天，于是「分母 = 记录天数」和「分母 = 7」两种实现输出一模一样 ——
`1/5` 和 `1/7` 无法区分，硬编码 7 能过掉全部 21 条检查。加上这一份数据之后，T19 的独立重算
（分母取 `len(items)`）会立刻把硬编码 7 的实现判为不一致。**先让新数据跑过既有检查，而不是
为新数据发明新断言** —— 这是本仓库最便宜、也最有效的找缺陷方式。

⭐ **T20 来自「一个看起来完全正常的错误数字」。** `CN-02` 的第二周（`2026-W39`）连续 5 天没称重，
只有 `09-21` 和 `09-27` 两个读数。旧实现把这两个数平均成「7 天均值 64.25 kg」，再与上周
64.58 kg 相减，输出 `−0.33 kg`。这个数字**没有任何异常特征**：0.5%/周，正落在目标区间里，
周复盘于是会写「维持计划」。而它衡量的是水分和一台新秤，不是脂肪 ——
**一个看起来正常的错误答案，比一个明显离谱的错误答案贵得多。**

修法是给「7 天均值」这三个字加一个前提：一周 7 天里至少 4 天有读数，否则均值不成立，
趋势也就无从谈起，两列一起退化为 `——`。同一份数据里，W38 的 4 次称重仍然算得出均值 ——
**阈值两侧各有一个真实样本**，所以「要求 7 天全勤」和「2 天就平均」两种实现都会在这个档案上翻车。
这就是 T20 里那对 3 天 / 4 天探针的来历：与 T19 的 135 g / 134.9 g 同理，边界两侧各放一个，
改错方向时交叉验证才不会陪着一起错。

⭐ **T16 / T16b 只扫清单里的文件**（`SAMPLE_SOURCE_DOCS`）。新增一份含示例的文档时，必须把它加进
清单 —— 否则这类缺陷会从缺口里漏过去，`docs/dev-guide.md` 就曾经这样漏过一次。

## 三、L2 工作流测试（人工，逐条打勾）

### 3.1 拍餐工作流

- [ ] 只给餐前照片，能产出完整结果
- [ ] 只给文字描述（"鸡胸肉饭"），能产出结果
- [ ] 输出包含置信度，且给了理由
- [ ] 输出包含进食顺序，顺序为 蛋白 → 蔬菜 → 主食
- [ ] 遇到炒菜/煎炸，**主动追问油/黄油/酱汁**
- [ ] 每个数字都可单步修改
- [ ] 修改后 `edited` 字段被写入
- [ ] **餐后追问一次进食顺序，并把答案写进 `order_ok`**（这是唯一能验证 §4.2 规则有效性的数据）
- [ ] 整个流程操作 ≤ 15 秒

### 3.2 训练工作流

- [ ] 视频能识别动作（硬拉 / 深蹲 / 卧推）
- [ ] 视频能识别次数
- [ ] **系统明确要求用户提供重量**（不自行推断）
- [ ] 同一动作 <2 次记录时，不给负重建议并说明原因
- [ ] 全组达标且 RPE 达标 → +2.5kg（上肢）/ +5kg（下肢）
- [ ] 次数未达标 → 减一个增量并保持
- [ ] 输出含"引用了哪条规则"
- [ ] 消耗标注为 `estimated`
- [ ] **训练记录的 `source` 写作 `video+voice`**（重量来自语音），不是 `video` —— `video` 不是合法取值

### 3.3 日报工作流

- [ ] 一屏可读完（手机不滚动）
- [ ] 含四项：缺口 / 蛋白 / 睡眠 / 训练
- [ ] 缺口使用 `ok / light / high`，**无红黄绿配色**
- [ ] "What changed" **恰好一行**
- [ ] 无评判性词汇（failed / over budget / cheating / bad day）
- [ ] 休息日显示 `rest`
- [ ] 每个数字带来源

### 3.4 周复盘工作流

- [ ] 用 7 天均值，不用单日体重
- [ ] 展示重算的算术过程
- [ ] **蛋白达标 <5/7 天时，不改热量目标**
- [ ] 每周最多改一个变量
- [ ] 写入 `profile.md` 前请求确认

## 五、L4 跨模型测试

**目的**：验证"模型可换"这一核心主张是否真的成立。

### 5.1 方法

同一份输入（`fixtures/CN-01-li-ming.md` 的第 3 天），分别喂给三个不同厂商的模型，要求按 `SKILL.md` 输出。

### 5.2 比对项

| 项 | 通过标准 |
|---|---|
| 输出结构一致性 | 三个模型的输出字段名完全一致 |
| 进食顺序 | 三个模型给出的顺序符合 §4.2 规则 |
| 追问隐藏油脂 | 三个模型都追问了 |
| 数值差异 | kcal 估算差异 < 25%（可接受），**结构必须 100% 一致** |

⭐ **关键判据**：**允许数值不同，不允许结构不同。** 结构是由契约决定的，与模型无关；数值才依赖模型能力。

### 5.3 记录方式

把结果记入 `docs/testing-log.md`（首次测试后创建），格式：

```
日期 | 模型 | 输入 | 结构一致(Y/N) | 数值偏差 | 备注
```

## 六、L5 饮食结构测试（本项目最重要的人工测试）

### 6.1 为什么单列一层

【事实】现有英文拍照识别产品的公开短板：
> *"users predominantly cooking East/South Asian or West African home food should weight photo-AI scores cautiously"*

**非西方餐食的识别与追问，是整个品类的盲区。** 这既是我们的机会，也是必须专门测的地方。

### 6.2 测试矩阵

用 `examples/fixtures/` 中的 9 个合成档案，逐一验证：

| 菜系 | 测试重点 | 通过标准 |
|---|---|---|
| 中餐（家常/外卖） | 混合菜的置信度是否降低 | 混合菜必须标 `medium` 或 `low` |
| 川菜 | 油量是否被追问 | 必须追问 |
| 墨西哥菜 | 玉米饼/豆类/奶酪的组合是否被拆分 | 至少拆出 3 项 |
| 西非菜 | 炖菜类是否被识别为整体 | 允许整体估算，但置信度必须 `low` |
| 南亚素食 | 是否遗漏酥油（ghee） | 必须追问 |
| 英式 | 啤酒是否被记录 | 必须记录并排在进食顺序最后 |

### 6.3 失败判定

**如果某个菜系在三份样本上有两份识别失败 → 触发产品改进**：在该菜系的 prompt 中增加追问模板。

## 七、合成测试数据（`examples/fixtures/`）

### 7.1 ⚠️ 强制红线

| 规则 | 说明 |
|---|---|
| **必须标注 `SYNTHETIC`** | 每个文件头 + `fixtures/README.md` |
| **禁止用于** | 宣称真实用户数、投资人材料、媒体报道、任何暗示"已有 N 位用户"的场景 |
| **禁止使用** | 真实姓名、真实照片、真实账号、真实联系方式 |
| **允许用于** | 软件测试、界面演示、跨饮食结构验证、文档示例 |

**【结论】把假数据做得像真人，是为了测出真问题；不是为了把它当成真的。**

### 7.2 组成

| 文件 | 内容 |
|---|---|
| `fixtures/README.md` | 合成数据总说明 + 红线 |
| `fixtures/personas.md` | 9 个虚构用户档案（基线 + 饮食结构 + 测试目的） |
| `fixtures/CN-01.md` ~ `fixtures/IN-01.md` | 日志文件：6 份完整 7 天；`CN-01` 与 `CN-02` 各带一个额外的 ISO 周（后者连续 5 天缺测体重）；外加 `DE-01` 的 5 天部分周 —— 共 75 天 |

### 7.3 保真度要求（"看上去像真人"的具体定义）

每个档案必须包含：

1. **不完美的数据** —— 有漏记的餐、有 `unknown` 的重量、有被编辑过的估算
2. **真实的不规律** —— 周末饮食失控、某天睡 4 小时、连续两餐外食
3. **地域性饮食** —— 用真实的当地菜名，不用翻译腔
4. **可追溯的编辑记录** —— `edited:` 字段里写清改了什么、为什么
5. **异常与失败** —— 至少有一天完全没记录训练，至少有一天蛋白严重不达标

**不满足以上任一条的档案，视为不合格。**

## 八、手工阶段验收（真实用户，非合成）

区别于合成数据，这是**唯一能验证需求真实性**的测试。

| 项 | 方法 | 判据 |
|---|---|---|
| 可行性 | 3 个真人 × 14 天 | 42 份日报产出 |
| 留存 | D19 提问 | **≥2 人回答"我会自己继续"** |
| 耗时 | 计时 | 单次拍餐记录 ≤15 秒 |
| 准确性 | 对比用户的实际纠正率 | 记录 `edited` 的比例作为基线 |

⚠️ **<2 人说"会自己继续" → 判定为分发问题而非产品问题 → 停止，不进入下一阶段。**
